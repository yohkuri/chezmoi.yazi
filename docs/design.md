# chezmoi.yazi design

Status: implemented and tested on the baseline runtime, 2026-09-18.
See [README](../README.md) for installation and [validation](validation.md)
for measured evidence and remaining limits. This document retains the design
rationale; implementation notes below describe departures from its sketches.

## Scope and decisions

The first release displays chezmoi management and status information for local
destination paths in Yazi's current file list. It uses a managed-path snapshot
per acquisition pass and caches asynchronously acquired status records. It adds
a
linemode child without replacing the user's selected linemode.

The user selected these defaults:

- Refresh on relevant Yazi activity and provide an explicit refresh command.
  Do not run a periodic polling loop.
- Enable recursive directory summaries by default, with an option to disable
  them.
- Replace old status columns with explicit failure signs when a refresh fails
  (D3-A).
- Evaluate templates and encrypted entries through chezmoi within the selected
  query scope (D4-A).

The accepted baseline also includes a management marker, the original two
status columns, and styles/signs configured through `[chezmoi]` in `theme.toml`
or `flavor.toml`.

Source-tree display, automatic apply/add/re-add operations, multi-configuration
switching within one Yazi instance, and a background daemon are outside the
first release. Source paths can be supported later using chezmoi's mapping;
source filename attributes must not be decoded by the plugin itself.

The initial integration baseline is Yazi 26.9.1 and chezmoi 2.72.2 on macOS.
The `@since 26.9.1` annotation enforces the minimum Yazi version. Other
platforms and chezmoi versions require separate verification.

## Status semantics

`X` compares the last state written by chezmoi with the actual destination.
`Y` describes the change from the actual destination to the target state.
Keep both raw characters; do not reduce them to one priority code.

| Code | Meaning in X | Meaning in Y |
| --- | --- | --- |
| Space | No reported change | No reported change |
| A | Created | Will be created |
| D | Deleted | Will be deleted |
| M | Modified | Will be modified |
| R | Not applicable | Script will run |

An entry is `clean` only when it belongs to a successfully acquired managed
index and a successful, complete status query covering that entry omits it.
This means "no difference reported by this status query", not necessarily that
all historical states are identical. In particular, status can omit an entry
whose actual and target contents match even if the last-written contents differ.

Treat removal entries, including `.chezmoiremove` and removals generated by
`exact_` directories, as managed operations. A management marker does not mean
that a corresponding regular source file exists.

## Display contract

With directory summaries enabled, the logical layout is `MXYD`:

- `M`: membership marker, `C` for a known managed entry.
- `X` and `Y`: the entry's own status, including spaces.
- `D`: descendant summary, only meaningful for directories.

Examples below use quoted strings so that spaces are visible as positions.

| Display | Meaning |
| --- | --- |
| `"C   "` | Managed entry, no reported own or descendant change |
| `"C M "` | Managed entry that apply would modify |
| `"CMM "` | Actual file changed; apply would also change it |
| `"C D "` | Managed removal operation |
| `"C  *"` | Directory is clean itself and has a changed descendant |
| `"C M*"` | Directory itself and at least one descendant differ |
| `"C  ?"` | Own status is known; descendant scan is pending or incomplete |
| `"C?? "` | Membership is known; own status has not been obtained |
| `"C!! "` | Own status query failed, under selected decision D3-A |
| `"?   "` | Membership has not been determined; directories also show `?` in D |
| `"!   "` | Membership query failed; directories also show `!` in D |
| `"    "` | Known unmanaged entry without a relevant summary |

Keep membership and descendant information independent. If an ancestor is not
itself a managed entry, do not invent `C` solely because it contains managed
descendants. Such an ancestor may still have a descendant indicator.

When summaries are disabled, omit the D slot for all rows. When enabled,
reserve it for files as well as directories so the columns align. Out-of-scope
URLs, such as unsupported remote URLs, render nothing.

Each logical slot has a width based on the maximum terminal display width of
its configured signs. ASCII defaults use one cell per slot. Pad shorter signs;
do not truncate user signs in the middle of Unicode grapheme clusters. Empty
signs are allowed as deliberate customization. Reject control characters in
signs. Recompute widths when the theme changes.

Follow git.yazi's default hovered-row behavior: retain the signs and inherit
the row highlight instead of forcing status foreground colors on that row.

## Directory summaries

The summary covers all applicable managed descendants, including missing
destination entries and pending scripts. It is not limited to descendants
already visited, currently visible, or allowed by Yazi's hidden-file filter.
Do not create synthetic file-list rows for missing entries.

Store the directory's own XY pair separately from its summary. Never combine
the X of one child and the Y of another into a fabricated status pair.

| Descendant scan result | D slot |
| --- | --- |
| Complete, at least one difference | `*` |
| Complete, no differences | Space |
| Pending or incomplete, no confirmed difference | `?` |
| Failed, no confirmed difference | `!` |
| Partial, at least one confirmed difference | `*` using the partial style |

The partial style indicates that `*` confirms at least one change but does not
promise complete coverage. The model retains completeness even when the sign
is unchanged. A failed recursive query must not overwrite a separately known
own-status result. Attempt a non-recursive own-status query when appropriate.

Scanning directories visible at the destination root can cover most managed
entries. Recursive aggregation therefore has a real cost even when only a few
directory rows are visible.

## Acquisition and data model

Use one chezmoi context per Yazi instance. Resolve its destination through
chezmoi, honoring the selected configuration; do not assume that it is HOME.
Configuration selection must be the same for discovery, managed, and status
commands. Obtain only the required path metadata rather than logging a full
configuration dump that may contain user template data.

Use `Command` with separate arguments, a closed stdin, no pager, no color,
no progress output, and no TTY prompts. Place `--` before target arguments.
Do not build shell command strings. Output framing, filtering, and path style
are owned by the plugin, not inferred from user display preferences.

The full-evaluation command shapes are:

```text
chezmoi [context/noninteractive flags] managed
  --include=all --exclude=none --path-style=absolute --nul-path-separator

chezmoi [context/noninteractive flags] status
  --include=all --exclude=none --path-style=absolute
  --recursive=false -- <managed direct targets...>

chezmoi [context/noninteractive flags] status
  --include=all --exclude=none --path-style=absolute
  --recursive=true -- <managed directory roots...>
```

These normalized filters intentionally describe unfiltered status, even when
the user's bare `chezmoi status` has a configured exclusion. Under selected
decision D4-A, the first release uses full evaluation within the query scope.
Skipped entries must never become clean or unmanaged implicitly.
Full evaluation also explicitly sets `--skip-secrets=false` on these commands.

Discovery produces an exact-path membership map; the implementation derives
ancestry for the requested scope without retaining a separate ancestor index.
Normalize path syntax consistently with Yazi's local URLs without resolving
symlinks to their referents. Use path-component boundaries for ancestry;
`/a/b` is not the parent of `/a/bc`. Do not lowercase paths indiscriminately.

Original logical record sketch (the implementation uses smaller records):

```text
context:
  identity, destination, epoch, managed_generation,
  membership_health, managed_paths, ancestor_index

entry:
  membership = managed | unmanaged | unknown,
  own = { health, x, y, observed_at, managed_generation },
  descendants = { health, changed, complete, observed_at }

query:
  epoch, request_id, scope, coverage, started_at, outcome
```

`health` distinguishes pending, ready, stale, failed, and deliberately skipped
results. Membership failure belongs to `membership_health`; it is not another
meaning of unmanaged. Last-good results can be retained internally for
diagnostics, but D3-A prevents displaying them as current after a failed query.

The query planner batches ordinary direct targets and removes redundant
recursive roots. It splits arguments by byte budget to avoid command-line
length limits. It never passes an empty target list to status accidentally,
because that would request the entire context.

Each result carries explicit coverage. Only a successful, fully parsed result
can establish clean status for an omitted path within that coverage. Replace
the covered snapshot rather than only merging changed entries. Rebuild
ancestor summaries so that resolved differences disappear.

The managed index is a snapshot too. Refresh it with a new observation pass so
that newly managed entries, forgotten entries, and dynamic removals from
`exact_` directories are rediscovered. A failed index refresh does not turn the
previously known paths into unmanaged entries.

## Parsing and failures

Parse managed paths using NUL separators. Parse status by preserving the first
two bytes and the path starting after the single separator; never trim the
whole line, split paths on whitespace, or strip quotation marks.

The tested status command emits embedded filename newlines literally and has
no NUL output flag. Before using a recursive line-oriented status batch,
inspect the relevant managed paths, including descendants. If any contain
CR/LF, enumerate that affected scope into explicit non-recursive targets;
query exceptional paths individually and match the entire returned path and
record framing. Ordinary paths can still be batched. Runtime fixtures verify
this fallback with directory summaries and removal entries.

Validate the complete output against the query scope and known index before
publishing. Unexpected records, unknown codes, inconsistent membership, or
ambiguous framing trigger invalidation/re-discovery or an explicit unknown
result, never a guess. Changes during discovery and status acquisition cannot
be made transactional by the plugin; one bounded re-discovery may recover a
race, with further recovery left to the next refresh. The current implementation
chooses explicit failure and leaves re-discovery to the next refresh.

On a failed batch, use bounded subdivision to salvage independent valid
targets. Impose a total retry budget; a broken shared configuration must not
cause one subprocess per managed file. A failed directory scan keeps that
summary incomplete even if some direct targets can be recovered.

Check spawn errors, nonzero exit status, parse errors, and cancellation
separately. Automatic attempts use backoff; explicit refresh can request a
new attempt. Notifications are deduplicated. Do not automatically echo raw
stderr, template contents, or credential command output into notifications
or persistent logs.

## Refresh and concurrency

Approved behavior is activity-driven refresh plus an explicit command:

```toml
[[mgr.prepend_keymap]]
on = ["c", "r"]
run = "plugin chezmoi -- refresh"
desc = "Refresh chezmoi status"
```

The key is an example, not an automatically installed binding. Refresh must
invalidate the context's old results, refresh membership, and actively query
the current scope. Merely clearing a cache and waiting for a future fetcher
call would not fulfill this command's contract.

Use fetcher execution and directory navigation as refresh opportunities.
Coalesce queued work and share one worker. A two-second record reuse
window avoids repeated commands for the same paths within a burst.
The window is a cache policy, not a timer or a guarantee that the display
updates every two seconds. Explicit refresh bypasses it.

Scrolling and tab switching must obtain the correct scope when fetchers run.
Verify actual event/fetcher behavior on the baseline runtime before promising
additional automatic triggers. In particular, a template edited outside Yazi
while the view is stationary is not guaranteed to trigger a refresh.

Serialize chezmoi work per context initially. Retain only the latest relevant
queued scope where requests supersede one another. Manual refresh advances
the epoch; results from a previous epoch cannot publish. A single serialized
worker makes separate scope request IDs unnecessary. Navigation
must not publish one directory's result as another's.

All state-transfer wrappers stay unconditional at main.lua top level. Keep
subprocess work, parsing, and indexing out of the render callback. Rendering
reads a prepared record in constant time per row. Theme reload only rebuilds
styles, signs, and widths; it does not invoke chezmoi.

A bounded direct-child lifetime is implemented with `read_line_with`, a shared
deadline, `try_wait`, and `start_kill`. Runtime tests cover silent children,
early stdout closure, partial stdout, stderr backpressure, and termination.
stderr is discarded to avoid both secret exposure and partial-stdout loss
from Yazi 26.9.1's concurrent stream reads. No Python or GNU timeout dependency
is needed by the plugin. Arbitrary grandchildren and termination during Yazi
exit are not covered by the timeout guarantee; see the README's limits.

## Public configuration

The minimal interface below is implemented. README lists all options.

```lua
require("chezmoi"):setup {
  order = 1600,
  directory_summary = true,
}
```

`order = 1600` uses a separate position from git.yazi's default 1500;
coexistence and ordering are covered by the optional git.yazi runtime fixture.

```toml
[[plugin.prepend_fetchers]]
url = "*"
run = "chezmoi"
group = "chezmoi"

[[plugin.prepend_fetchers]]
url = "*/"
run = "chezmoi"
group = "chezmoi"
```

Use the same plugin entry for setup, fetch, and refresh so that they share
state. Fetcher completion/retry semantics must match Yazi 26.9.1; do not copy
an older installed git.yazi's boolean-return contract without verification.

```toml
# theme.toml / flavor.toml
[chezmoi]
managed   = { fg = "cyan" }
unmanaged = { fg = "darkgray" }
clean     = { fg = "green" }
added     = { fg = "green" }
modified  = { fg = "yellow" }
deleted   = { fg = "red", bold = true }
run       = { fg = "magenta" }
changed   = { fg = "yellow" }
unknown   = { fg = "darkgray" }
error     = { fg = "red", bold = true }
partial   = { fg = "yellow", underline = true }
stale     = { fg = "darkgray", dim = true }

managed_sign   = "C"
unmanaged_sign = ""
clean_sign     = " "
added_sign     = "A"
modified_sign  = "M"
deleted_sign  = "D"
run_sign      = "R"
changed_sign  = "*"
unknown_sign  = "?"
error_sign    = "!"
```

Read the effective configuration from `th.chezmoi`; let Yazi handle theme and
flavor loading. The runtime flavor fixture verifies fallback and key-level
overrides (style properties are not merged individually). `partial` styles a
confirmed summary with incomplete coverage.
`stale` styles old data during an in-flight refresh. After a failed query,
explicit failure signs replace that old status under D3-A. Theme configuration
never changes the semantic status model.

## Confirmed product decisions and alternatives

The user selected A for both D3 and D4 on 2026-09-18. The tables retain the
alternatives and their tradeoffs as decision rationale, not pending choices.

### D3: display after a status refresh fails

| Option | Example | Benefit | Cost |
| --- | --- | --- | --- |
| A: replace old XY with failure signs (selected) | `C!!` | Does not present an old difference as current | Previous useful detail is hidden |
| B: retain old XY with stale styling and a failure indicator | Old `CMM`, dimmed, plus a dedicated failure indicator | Previous detail remains visible | Needs an additional display position or richer format; colors alone may be hard to distinguish |

Decision: A. Last-good history is optional and is not retained separately.
During an automatic in-flight
refresh, the old record may remain with the stale style; after failure, use
explicit failure signs. Membership failure similarly invalidates the visible
membership claim. Do not replace a known own-status failure with a descendant
summary's failure or vice versa.

### D4: evaluation of templates and encrypted entries

| Option | Behavior | Benefit | Cost |
| --- | --- | --- | --- |
| A: full evaluation through chezmoi (selected) | Evaluate the entries required by the selected scope, including templates and encrypted files | Preserves actual chezmoi status semantics | Secret providers, decryptors, hooks, or external resources can add latency or require credentials |
| B: explicitly limited evaluation | Skip selected categories and display their status as unknown/skipped | Reduces selected external dependencies | Some managed statuses remain unavailable; discovery must still preserve their membership |

Decision: A for the first release, with closed stdin, no TTY prompts,
and a bounded runner whose runtime validation is required above. These controls
do not make
template evaluation side-effect-free or prevent every external program from
opening its own UI. The plugin does not invoke apply or execute apply scripts,
but chezmoi configuration hooks and template functions can invoke commands.

Keep external-refresh behavior consistent with the selected chezmoi context
and explain that it may refresh resources; do not silently force cache-only
evaluation while claiming equivalence to current target state.

Alternative B is deferred. A future limited mode would need first-class
partial results. Adding
`--skip-secrets` and treating absent output as clean is not sufficient, and
that flag does not suppress every arbitrary command in a template. No excluded
entry may be reported as unmanaged simply because discovery skipped it.

All four presented product choices are now confirmed and implemented.

## Validation and implementation sequence

1. Verify the runtime adapter against the confirmed decisions: fetcher retry,
   manual refresh dispatch, theme/flavor data, and bounded child processes.
2. Implement the parser and state reducer with focused tests for XY fidelity,
   coverage, membership changes, stale generations, and summary completeness.
3. Implement scoped CLI acquisition, special-filename fallback, and bounded
   recovery using isolated destination/source/config/state fixtures.
4. Integrate linemode rendering and run real Yazi checks in isolated config,
   cache, and state directories. Inspect that run's logs and display output.

Required acceptance cases include:

- Clean, unmanaged, `" M"`, `MM`, `DA`, `" D"`, and pending `" R"` states.
- Templates, symlinks, directory attributes, `.chezmoiignore`,
  `.chezmoiremove`, and `exact_` removal of newly created extra entries.
- Missing targets reflected in ancestor summaries without synthetic rows.
- Own status preserved independently of descendant differences and failures.
- Space, Japanese, quotation-mark, backslash, CR/LF, and leading-dash names.
- Navigation away/back, scrolling, tab switching, manual refresh while an
  earlier query is running, and adding/forgetting managed entries externally.
- A broken template affecting a recursive query while unrelated valid
  targets remain recoverable within the retry budget.
- Theme overrides, flavor fallback, theme reload, hovered-row contrast,
  customized wide/empty signs, and coexistence with git.yazi.
- A stalled child, a missing executable, a failed membership query, and a
  parser failure never producing a false clean/unmanaged result.

Measured CLI acquisition on small and large synthetic trees and the tested
acceptance cases are recorded in [validation](validation.md). The checklist
above remains the intended coverage, not a claim that every case/platform has
been exercised. Cache/retry/timeout constants remain configurable defaults.

Isolated CLI probes on chezmoi 2.72.2 confirmed:

- A direct status query for an unmanaged path fails.
- A broken file template can fail a full status query while a targeted valid
  file succeeds; managed still lists the broken template's destination.
- Managed supports NUL path separation and structured all-path mapping;
  status emits literal embedded filename newlines.
- The tested status command rejects `--path-style=source-absolute`, despite
  the shared documentation listing additional path styles.
- Local edits after apply produce `MM`, source-only edits produce `" M"`, and
  deletion after apply produces `DA` in the tested fixtures.
- Managed includes removal operations created by `.chezmoiremove` and by an
  `exact_` directory's extra destination file.
- Recursive status reports such an extra file as `" D"`; non-recursive status
  of the containing directory alone omits that child operation.

These initial probes validate CLI behavior. Subsequent real-Yazi integration
checks are recorded separately in [validation](validation.md).
